# "点拆解会卡死"排查记录

这份文档把"已确认"和"未确认"分开写。旧版 README 把两件事混成了一件，读起来像已经破案。

## 1. 现象

用户报告：拖动拆解滑块时页面卡死。表现为画面定格，但按钮还能点、对话框还能弹。

## 2. 已确认的健壮性缺陷

主循环的 `requestAnimationFrame` 原本排在函数末尾：

```js
function frame(){
  renderer.render(scene, camera);
  // …四十行业务逻辑…
  requestAnimationFrame(frame);   // ← 最后一行
}
```

任何一行抛错，下一帧就永远排不上。页面 DOM 还活着，但渲染彻底停住 —— 症状与用户描述一致。

**这是代码读出来的确定事实，不是推测。**

修法：

```js
function frame(now) {
  try { frameBody(now); } catch (e) {
    if (errs.length < 40) errs.push('frame: ' + (e && e.message || e));
  }
  requestAnimationFrame(frame);
}
```

以及把 `history.replaceState` 单独兜住（拖滑块时会被浏览器节流，某些情况下直接抛错），自动同步间隔从 700 ms 放宽到 2500 ms。

## 3. 未确认的部分

**这次卡死的根因没有被证实。** 缺的东西：

- 没有异常栈。`errs` 只存 `e.message`，没有 `e.stack`
- 没有故障注入。没做过"人为在 frameBody 里抛错，对比修复前后的复现与恢复"
- 没有修复前后的复现对照。用户那次卡死的现场已经过去了
- `replaceState` 那条也没有证据闭环：说"实测连打 160 次会无响应"，但没记录时间窗口、浏览器版本、调用频率与页面上其他负载

所以准确表述是：**发现并修掉了一个足以解释该症状的健壮性缺陷；该用户的这次卡死是否由它引起，未证实。**

## 4. 复现尝试记录

用有头 Edge + 真 GPU 跑 CDP：连续拖 40 秒拆解滑块（868 次 input 事件）、把每个按钮点一遍 —— 都没复现。

同一次测量里的帧时间中位 6.1 ms **已从 README 撤下**，原因是缺测试条件：没记 CPU、GPU、浏览器版本、视口、DPR、特效状态和计时方法。6.1 ms 也可能是 CPU 回调耗时，不一定是完整帧间隔或 GPU 时间；只给中位数也不能说明拖动时没有卡顿。

要重新给性能数字，至少需要：固定版本与硬件、明确计时对象（`performance.now()` 差值 / CDP Tracing / GPU timer query）、报告 P50/P95/P99、说明特效开关状态。

## 5. 现在的异常处理仍不完整

`errs` 有 40 条上限，但没有：

- 限频与去重 —— 持续异常会在每帧重复失败、重复记录
- 可恢复 / 致命的分级 —— 现在一律"记一笔，下一帧照排"，而某些异常（例如渲染器上下文丢失）下一帧必然再错
- 用户可见提示 —— 状态栏没有提示，用户只知道"画面不动"

**按钮能动不等于渲染或应用状态健康。** 这条限制写在这里，不假装修好了。

## 6. 顺带记一个"看起来像 bug 但不是"的

火星 sprite 的位置：引擎整体挂在 `engine` 组上并有 `LIFT` 抬升。只做 `bankToWorld` 得到的是**整机局部**坐标，直接喂给 `scene` 上的 sprite 会落在油底壳那一层。必须 `engine.localToWorld(bankToWorld(...))`。这类"两次坐标系"的错误在场景里排查起来比几何穿模更费时。
